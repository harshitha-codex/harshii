CHAPTER 6: DISCUSSION

This chapter provides a comprehensive and critical analysis of the design decisions, empirical findings, and operational performance of the LinkSus – Cloud-Based ML Phishing Detection System. The discussion contextualizes the results obtained from the evaluation of the hybrid classification model, analyzes key findings derived from feature engineering and explainability integrations, addresses the challenges encountered during the development lifecycle, and compares the platform’s performance with traditional and modern security approaches.

6.1 Analysis of System Performance
The empirical evaluation of the LinkSus platform demonstrates that combining lexical character-level features with handcrafted structural indicators yields a robust classifier capable of generalizing to unseen phishing attempts. The Linear Support Vector Classifier (LinearSVC) achieved a classification accuracy of 92% on a balanced test set comprising 12,007 sample URLs. This performance is particularly significant given the sparse and high-dimensional nature of the text features generated by the TF-IDF vectorizer. LinearSVC is mathematically suited for this classification task because it scales well to high-dimensional datasets. By finding an optimal separating hyperplane that maximizes the margin between legitimate and malicious URLs, the model generalizes effectively without encountering the overfitting issues common in deep neural networks when trained on tabular and sparse text inputs.

During training, class-weight balancing (class_weight='balanced') was applied to resolve the inherent risk of model bias. Phishing datasets from public repositories often suffer from class distribution imbalances, which can cause standard machine learning models to favor the majority class. In security applications, this bias leads to high false-negative rates, meaning actual phishing URLs pass through undetected. Adjusting the class weights in the LinearSVC loss function penalizes misclassifications of the minority class more heavily, producing a balanced decision boundary. The results in Table 5.12 confirm this balance: the precision for phishing URLs ('bad') reached 94% with a recall of 89%, while legitimate URLs ('good') achieved a precision of 90% and a recall of 94%. This configuration balances safety (high recall on phishing) and usability (high precision to prevent false alerts on legitimate sites).

Standardizing the handcrafted features was also critical to the model's performance. The 19 handcrafted features include both binary variables (such as "Contains 'login'" or "Suspicious TLD") and continuous numerical counts (such as "URL Length" or "Digit Count"). Without normalization, continuous features with larger scales—such as a URL length of 250 characters—would dominate the decision boundary during SVM gradient optimization. Applying StandardScaler standardizes the features to have a mean of 0 and a variance of 1, ensuring that each feature contributes proportionately to the classification decision.

Analysis of the misclassified cases (the remaining 8% error rate) shows that false positives are typically caused by legitimate subdomains containing security-related keywords (e.g., "secure-update.company-portal.com"), while false negatives occur with short, obfuscated redirection URLs that lack standard lexical patterns (e.g., brand names or scam keywords). Incorporating whitelists and free-host blacklists at the pre-classification stage helps mitigate these errors for common domains.

6.2 Key Findings
The development and evaluation of the LinkSus platform yielded several key findings regarding feature selection, explainability, and multi-modal input processing:

* **Hybrid Stacking of Textual and Structural Features:** The combination of character-level TF-IDF vectorization and handcrafted feature extraction outperforms classifiers that rely on a single feature type. The character-level TF-IDF vectorizer (configured for 1-to-2 n-grams with 3,000 max features) captures the character distributions of phishing URLs, such as spelling variations of popular brands. The 19 handcrafted features capture structural patterns (e.g., subdomain counts, TLD anomalies) and semantic indicators (e.g., scam keywords). Stacking these features into a unified sparse matrix provides the classifier with both statistical and structural cues, improving detection of lookalike domains and brand spoofing.

* **String Similarity Metrics in Lookalike Detection:** TYposquatting and homograph attacks remain common entry points for phishing campaigns. Attackers register domains that closely resemble target brands, such as replacing the letter 'l' with a capital 'I' (e.g., 'paypaI.com') or using character combinations like 'rn' to mimic 'm' (e.g., 'arnazon.com'). To address this, LinkSus computes similarity ratios using difflib.SequenceMatcher. If a base domain’s similarity ratio to a list of target brands (google, amazon, paypal, facebook, microsoft, apple) falls between 0.70 and 1.0, it is flagged as a lookalike. This check is highly predictive, helping the model identify typosquatting domains that have not yet been blacklisted.

* **Explainable AI and Generative AI Integration:** Providing transparent decisions is essential for user trust. While machine learning classifiers provide binary classifications, they do not explain the logic behind a risk score. LinkSus addresses this by combining SHAP (SHapley Additive exPlanations) with the Google Gemini API. The SHAP Linear Explainer calculates the directional contribution of each handcrafted feature to the classification decision. These weights are then processed by the Gemini API (using the 'gemini-2.5-flash-lite' model) to generate a concise, two-sentence explanation of the specific risk factors. This approach translates mathematical feature weights into actionable descriptions for the user.

* **Multi-Modal Input Processing for Offline Security:** Phishing attacks have expanded beyond standard email links to physical-to-digital vectors, such as malicious QR codes ("quishing") on posters, parking meters, or receipts. To address this vector, LinkSus integrates a webcam-based QR scanner using the html5-qrcode library. Users can scan a QR code using their camera or upload an image file directly to the dashboard, extracting the URL and passing it through the detection pipeline. This interface extends real-time phishing detection from standard browser tabs to physical media.

6.3 Challenges Encountered
Several technical and architectural challenges were addressed during the implementation of the LinkSus system:

* **Subdomain Whitelist Bypassing:** An early implementation of the whitelisting module used broad string checks, such as `url.endswith(safe_domain)`. This created a security vulnerability: an attacker could register a domain like `verify-paypal.com`, which would match the whitelist check for `paypal.com` and bypass the classifier. To resolve this issue, the whitelisting logic was updated to verify that the extracted domain is either an exact match for the safe domain or a valid subdomain preceded by a dot notation (e.g., `mail.google.com` matches `google.com`, but `verify-google.com` does not).

* **Feature Imbalance and Standardization:** The 19 handcrafted features contain variables with significantly different scales. Continuous variables like URL length (ranging from 10 to 300+ characters) and digit counts can dominate binary indicator variables (0 or 1) during SVM optimization. Standardizing the features using StandardScaler resolved this scaling discrepancy, allowing binary indicators like "Contains Phishing Phrase" to influence the classification decision alongside continuous features.

* **Generative AI Latency and Cache Management:** Integrating the Google Gemini API to generate explanations introduces external network calls, adding 1 to 2 seconds of latency. To prevent this from slowing down the user interface during repeated checks of the same URL, a cache dictionary was implemented. The system generates an MD5 hash of the URL and its classification verdict; if a match is found in the cache, it returns the cached explanation, avoiding duplicate API calls. If the Gemini API is unavailable, the backend falls back to listing the raw SHAP feature labels to ensure uninterrupted operation.

* **Chrome Extension CORS and CSP Configuration:** Implementing the Manifest V3 Chrome Extension introduced security constraints. Content Security Policies (CSP) restrict inline scripts, requiring all JavaScript handlers to be moved to external script files (`popup.js` and `background.js`). Additionally, Cross-Origin Resource Sharing (CORS) rules blocked calls from the extension to the local Flask server on `http://127.0.0.1:5000`. This was resolved by configuring the Flask-CORS library on the backend to allow requests originating from the extension's specific Chrome identifier.

6.4 Comparison with Existing Approaches
Traditional phishing detection systems rely on static blacklists, which struggle to protect users during the initial hours of an attack. LinkSus addresses this gap by using a machine learning classifier to analyze the structural and character patterns of URLs, identifying malicious links without relying on database updates.

Unlike standard machine learning models that function as black boxes, LinkSus integrates SHAP and Gemini to provide natural language explanations of its decisions, helping users understand why a link was flagged. Finally, by supporting both direct URL input and webcam-based QR code decoding, LinkSus provides a more versatile detection platform than standard browser extensions.
